## 1. Stack & Architecture Decisions

### Decision: Fullstack Next.js 14 App Router (TypeScript 5.x)
- **Rationale**: The project monorepo uses Next.js 14 App Router. Modules `AIT`, `EXP`, and `PRF` share this architecture. Implementing REST route handlers under `src/app/api/iac/` and the UI under `src/app/messages/` (Screens `COM048` and `COM065`) preserves total architecture consistency and single-process development.
- **Alternatives considered**:
  - Separate Express backend: Rejected; introduces extra server process, breaks Next.js monorepo layout, violates Constitution Principle III.
  - Real-time WebSocket (e.g. Socket.io): Rejected; spec explicitly states MVP Chat is HTTP request/response (`F-CHAT-02`: immediate delivery, no queue/socket required for MVP alpha). Polling or re-fetch on send satisfies all MVP requirements without external infrastructure.

### Decision: Storage Integration via JSON Runtime (`json-repository.ts`)
- **Rationale**: Per `AGENTS.md` and repository conventions, the working prototype on `main` stores runtime entities in `.demo-data/runtime.json` backed by seed data from `data/seed/*.csv`. The database schema `data/schema.sql` defines the canonical structure (`chat_sessions`, `chat_participants`, `chat_messages`). The JSON repository handles persistence for local dev and runs an isolated in-memory copy for automated tests.
- **Data structures implemented**:
  - `chat_sessions`: session ID, agency ID, provider ID, source, context IDs (experience, quote, booking), status (`Active` | `Closed`), started_at, last_message_at.
  - `chat_participants`: composite key (chat_session_id, user_id), last_read_message_id, unread_count.
  - `chat_messages`: message ID, chat_session_id, sender_user_id, text (max 4000), message_kind (`User Text`), sent_at, context IDs.

### Decision: At Most One Active Chat Per Agency–Provider Pair (`chat_one_active_pair_uq`)
- **Rationale**: `data/schema.sql:731` defines `UNIQUE (agency_id, provider_id) WHERE status = 'Active'` and `spec-IAC.md` §5.1 / `BR-004` requires reusing the active session.
- **Mechanism**:
  - When `POST /api/iac/sessions` is invoked with `initiator_id` and `recipient_id`, the service queries for an existing session where `status = 'Active'` between the pair.
  - If exists: returns `chat_session_id`, `chat_status: 'Active'`, and `is_new_session: false`.
  - If none exists: creates a new `chat_sessions` record, adds both participants to `chat_participants` with `unread_count = 0`, and returns `is_new_session: true`.

### Decision: Experience / Quote / Booking Context as Metadata
- **Rationale**: `spec-IAC.md` §10 Q4/Q5 and `data/schema.sql:752-755` specify that conversations do not fork into separate threads per experience or booking. Context is metadata attached to the session and/or individual messages.
- **Behavior**: Opening Chat from Explore or AI Matching attaches `experience_id` as session context and pre-populates an initial greeting or context block if specified, but routes into the single active conversation thread between the pair.

### Decision: Markdown & Content Security
- **Rationale**: `BR-007` requires plain text plus basic bold (`**text**`) and italic (`*text*` or `_text_`) markdown; `BR-006` mandates immutable messages without editing or deletion.
- **Validation**:
  - Input `message_text` trimmed; empty or whitespace-only messages rejected with 400 Bad Request.
  - Maximum length enforced at 4,000 characters per `BR-007` and `schema.sql:750`.
  - Client and server sanitize HTML to prevent XSS while safely parsing bold and italic markers.

### Decision: Unread Count and History Pagination
- **Rationale**: `spec-IAC.md` §10 Q10–Q12 and `BR-015`, `BR-017`.
- **Implementation**:
  - When User A sends a message in a session, User B's `chat_participants.unread_count` increments by 1.
  - When User B opens/fetches the message history of that session (`GET /api/iac/sessions/:id/messages`), User B's `unread_count` resets to 0.
  - Initial history query returns up to 50 messages ordered chronologically (oldest to newest for display, or newest first with cursor for pagination).

## 3. Business Rule Implementation Approach

| Business Rule | Implementation Approach |
|---|---|
| **BR-001** (Agency & Provider only) | Service layer validates that one participant is a Tour Agency and the other is a Local Provider. Reject other role combinations with 403 Forbidden. |
| **BR-002** (Participant isolation) | Every session and message query verifies `user_id IN (SELECT user_id FROM chat_participants WHERE chat_session_id = :id)`. Non-participants receive 403 Forbidden. |
| **BR-003** (Permission verification) | Verify active demo session cookie (`hab_demo_account`). Reject unauthenticated requests with 401 Unauthorized. |
| **BR-004** (Session reuse) | Atomic query for existing session where `agency_id = :agencyId AND provider_id = :providerId AND status = 'Active'`. Return existing ID if present. |
| **BR-005** (Session persistence) | Records persisted to JSON repository runtime (`.demo-data/runtime.json`) or test database; session remains Active until explicitly closed. |
| **BR-006** (Message immutability) | No PATCH or DELETE endpoints exist for `chat_messages`. Trigger/service checks reject mutation. |
| **BR-007** (Message format & length) | Zod validator: `z.string().trim().min(1).max(4000)`. Markdown parser renders bold and italic safely. |
| **BR-012** (Context association) | Context IDs (`experience_id`, `quote_request_id`, `booking_id`) stored in `chat_sessions` and `chat_messages` as metadata; not treated as file attachments. |
| **BR-013** (Chat list ordering) | Chat list sorted by `COALESCE(chat_sessions.last_message_at, chat_sessions.started_at) DESC`. |
| **BR-014** (Chronological messages) | Returned message history sorted by `sent_at ASC` (oldest first). |
| **BR-015** (Pagination) | Query limits initial fetch to 50 items. `before_cursor` supports fetching older messages. |
| **BR-016** (Role isolation) | Agency users see only Provider counterparts in chat list; Provider users see only Agency counterparts. |
| **BR-017** (Unread count reset) | Opening conversation history triggers `unread_count = 0` for the calling participant. |
| **BR-018** (No booking creation) | Chat service never creates or alters bookings. |
